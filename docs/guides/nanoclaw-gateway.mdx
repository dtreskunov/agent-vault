## Headless bootstrap (F10)

Run from the NanoClaw working directory:

```bash
agent-vault server --env-file .env
```

```dotenv
AGENT_VAULT_HEADLESS=true
AGENT_VAULT_REVEAL_DISABLED=true
AGENT_VAULT_MASTER_PASSWORD_FILE=/absolute/path/to/master-password
AGENT_VAULT_BOOTSTRAP_TOKEN_FILE=data/agent-vault/host-token
AGENT_VAULT_SOCKET_ROOT=data/agent-vault/sessions
AGENT_VAULT_UNMATCHED_HOST_MODE=tunnel
AGENT_VAULT_TELEMETRY=false
```

Only `AGENT_VAULT_*` keys are imported. Process variables win; values are
literal (no shell expansion). Single/double quotes and trailing comments are
accepted. Relative paths are relative to the working directory, not the env
file. Input settings accept `_FILE`; do not also set the plain variable.
The bootstrap-token path is an output, not a secret-file input.

Headless mode requires a nonempty master password,
`AGENT_VAULT_REVEAL_DISABLED=true` and foreground operation.
Both TCP listeners must bind to `127.0.0.1`; other `--host` values fail.
The UI, human-account routes, invites, cookie authentication and SMTP are off.
Normal agent-token REST access remains available, including vault creation
(the creating host agent becomes vault admin).

First boot creates `default` and the active instance-owner agent `nanoclaw-host`
with default-vault admin access. Its token is atomically written with mode 0600.
Later boots validate the existing file and never silently replace it. Keep
the token on the host, never in a container mount.

### Host-side REST administration

NanoClaw administers the headless gateway over REST, not the administrative
CLI. `agent-vault vault create` and `agent-vault vault service` require a
saved human login session; setting `AGENT_VAULT_TOKEN_FILE` does not make
those commands use the host agent's token.

The host's gateway client reads the token from the file configured by
`AGENT_VAULT_BOOTSTRAP_TOKEN_FILE` and sends it as `Authorization: Bearer
<host token>` on each request to `http://127.0.0.1:14321`. Keep token and
credential values out of logs, command-line arguments and container mounts.
The placeholders below are not literal values to send.

Create the group's vault; the host agent becomes its admin:

```http
POST /v1/vaults HTTP/1.1
Host: 127.0.0.1:14321
Authorization: Bearer <host token>
Content-Type: application/json

{"name":"ag-1780956116163-prz9h2"}
```

Set credentials, with the vault explicitly selected in the JSON body:

```http
POST /v1/credentials HTTP/1.1
Host: 127.0.0.1:14321
Authorization: Bearer <host token>
Content-Type: application/json

{"vault":"ag-1780956116163-prz9h2","credentials":{"EXAMPLE_API_KEY":"<credential value supplied by the operator>"}}
```

Replace the vault's complete service list:

```http
PUT /v1/vaults/ag-1780956116163-prz9h2/services HTTP/1.1
Host: 127.0.0.1:14321
Authorization: Bearer <host token>
Content-Type: application/json

{"services":[{"name":"example","host":"api.example.com/v1/*","auth":{"type":"bearer","token":"EXAMPLE_API_KEY"}}]}
```

PUT replaces all services, so include every service the vault should retain.
Credential and service writes are separate requests, not one atomic update.

Keep unmatched CONNECT targets in tunnel mode:

```http
PATCH /v1/vaults/ag-1780956116163-prz9h2/settings HTTP/1.1
Host: 127.0.0.1:14321
Authorization: Bearer <host token>
Content-Type: application/json

{"unmatched_host_mode":"tunnel"}
```

These calls select the vault in the body or URL; they do not require
`X-Vault`. Check each response before continuing: vault creation returns
`201`, and credential, service and settings writes return `200`.

### Bootstrap token recovery

For a missing or invalid bootstrap file, stop the service, then run:

```bash
AGENT_VAULT_HEADLESS=true \
AGENT_VAULT_REVEAL_DISABLED=true \
AGENT_VAULT_MASTER_PASSWORD_FILE=/absolute/path/to/master-password \
AGENT_VAULT_BOOTSTRAP_TOKEN_FILE=data/agent-vault/host-token \
agent-vault agent rotate nanoclaw-host
```

Use the same working directory, database configuration and HOME as the service.
This explicit local recovery unlocks the database, revokes the previous token
and atomically writes the replacement without printing it. It refuses to run
while the gateway PID file identifies a running process.

Fetch the public root CA from `GET /v1/mitm/ca.pem` after the TCP MITM listener
is ready. Use a service manager rather than `--detach`.

## Write-only credentials (F6)

Set `AGENT_VAULT_REVEAL_DISABLED=true` before upgrading a headless instance.
Startup fails if it is unset or false. The gateway persists
`reveal_disabled=true` in instance settings. Once enabled, clearing the
environment or setting the variable to false does not re-enable reveals.
Changing this boundary requires an explicit offline database change, not an
owner API request.

`GET /v1/credentials?reveal=true` returns
`403 {"code":"credential_reveal_disabled",...}` for every role, including
instance owners, human sessions and scoped tokens. The same policy covers
bulk reveals, single-key reads, OAuth access tokens and dynamic credentials.
The decision happens before decryption or dynamic-secret resolution.
Credential updates, key/metadata lists, OAuth status and normal proxy
injection remain available. OAuth metadata contains only public configuration,
timestamps and presence sentinels, never token or client-secret values.

`GET /v1/admin/settings` includes the effective `reveal_disabled` value.
Trying to update that field through `PUT /v1/admin/settings` returns `403`.
A policy lookup failure denies the reveal with `500` rather than exposing
values under a default policy.

## Socket sessions (F1)

Set `AGENT_VAULT_SOCKET_ROOT=data/agent-vault/sessions`. The gateway creates
this root if absent. The host creates a session directory below it and sends
an agent bearer token with each API request:

| Call | Result |
| --- | --- |
| `POST /v1/socket-sessions` with `{vault,label,dir}` | `201 {id,vault,socket_path}` |
| `GET /v1/socket-sessions` | `200 {items:[{id,vault,label,socket_path,created_at}]}` |
| `DELETE /v1/socket-sessions/{id}` | `204` (unknown or another host's ID: `404`) |

The directory must be absolute, existing and beneath the canonical root after
symlink resolution (`400` otherwise). Unknown vaults return `404`; no host
vault grant returns `403`; an already-bound directory or occupied socket path
returns `409`. Each host lists and deletes only its own sessions.

Mount the directory into the container and connect its relay to `egress.sock`.
The socket is mode 0666; restrict directory access and mount only the intended
session directory. Possession of the socket grants proxy access to its vault.
CONNECT and absolute-form HTTP use the existing injection, network guard,
request logging and per-vault limits. The per-IP auth-failure gate is skipped.
Client `Proxy-Authorization` is replaced with the internal identity and never
forwarded upstream. That identity is proxy-only and internally non-expiring
until deletion, so no seven-day renewal interruption occurs.

DELETE revokes the token, unlinks the socket and closes active connections,
including hijacked CONNECTs. Shutdown closes connections and unlinks sockets,
but preserves their identities and bindings. On restart, the gateway rebinds
the same socket paths with mode 0666 and retains each ID, vault, label and
creation time. Containers reconnect through their existing directory mount.
API passthrough via `agent-vault.internal` is not enabled.

Bindings and internal tokens are encrypted with the vault data key in the
existing database's instance settings. They are never stored as plaintext
token files. Only one gateway can own a socket root at a time. Changing the
root while persisted sessions exist fails explicitly rather than moving
container capabilities silently.

After an unclean exit, only known persisted socket paths are eligible for
stale-socket cleanup. An active listener or a non-socket file is never replaced.
Missing directories are logged and skipped, not recreated; their sessions
remain in GET so NanoClaw can reconcile them against live containers and
DELETE stale entries. Revoked identities or host memberships are not restored.
A POST with an occupied socket path still returns `409`. Use a fresh directory
for each spawn and do not remove live session directories until reconciliation.

## Blind tunnels (F2)

`AGENT_VAULT_UNMATCHED_HOST_MODE` accepts `tunnel`, `mitm` or `deny`. It defaults
to `mitm` for upstream compatibility; NanoClaw sets `tunnel`. Vault admins
override it with `PATCH /v1/vaults/{name}/settings` and
`{"unmatched_host_mode":"deny"}`. GET returns the effective value; PATCH with
an empty mode resets to the environment default. Invalid values fail closed.
Update the old `unmatched_host_policy` separately from the CONNECT mode.

For CONNECT only, services are matched by host and port across all paths.
Even a path-scoped or disabled service forces TLS interception on that target,
so a different path cannot evade injection or service enforcement. Unmatched
targets are either spliced as raw TCP (`tunnel`), rejected with 403 before
hijacking (`deny`), or handled by upstream's TLS interception (`mitm`).
Tunnels preserve the upstream certificate and encrypted bytes, without
credential injection. DNS/IP checks still run through the network guard at
dial time, including the unconditional cloud-metadata block.

Structured `CONNECT decision` logs contain the vault, host, port, decision,
bytes sent/received, duration and status; no headers or payloads are logged.
The standard request log also receives CONNECT status and duration. Existing
per-vault/actor proxy limits apply. Socket deletion terminates blind tunnels,
including half-closed connections.

The existing `unmatched_host_policy` still controls decrypted HTTP requests
and plain-HTTP forwarding; it is distinct from the pre-TLS CONNECT mode.
In particular, `unmatched_host_mode=deny` alone is not a plain-HTTP deny policy.

## Telemetry and fork guard (F9)

Telemetry is off by default. An operator can opt in with `--telemetry` or
`AGENT_VAULT_TELEMETRY=true` in an ordinary build; the environment takes
precedence. The installer beacon also requires explicit opt-in and still
honors `AGENT_VAULT_NO_TELEMETRY`.

For an unconditional telemetry-free gateway, build with:

```bash
CGO_ENABLED=0 go build -mod=readonly -tags notelemetry -trimpath -ldflags='-s -w' -o agent-vault .
```

This build excludes PostHog and machine-ID code. Neither `--telemetry` nor
an environment value can re-enable collection.

The Gateway foundation CI workflow runs on fork pushes and pull requests.
It fails if an `ee/` directory appears anywhere outside Git metadata, runs
the full suite with readonly modules, and checks the telemetry-free build.
Run the same source-tree guard locally with `python3 scripts/check-no-ee.py`.

## Reproducible validation

```bash
CGO_ENABLED=0 go build -trimpath -ldflags='-s -w' -o agent-vault .
go test ./...
go test -race ./internal/gatewayconfig ./internal/headless ./internal/blindtunnel ./internal/socketsessions
go test ./internal/socketsessions -run '^$' -bench BenchmarkInterceptedLatency -benchtime=1000x -count=1 -v
```

The benchmark compares direct HTTPS with HTTPS intercepted through a real
Unix socket, CA, store-backed session and encrypted credential injection.
It verifies each response and injection, warms each path with 100 requests,
then measures 1,000 sequential keep-alive requests per path. It reports p50
and fails if the added p50 is 5 ms or greater. No external services or real
credentials are used. Rate/concurrency enforcement remains enabled, with the
benchmark's token bucket raised to avoid intentional throttling. Connection
setup and cold-start TLS are excluded.

### Spike results (2026-10-20)

On Linux amd64, Intel N100, Go 1.25.0:

| Path | Samples | p50 |
| --- | --- | --- |
| Direct HTTPS | 1,000 | 0.1090 ms |
| Intercepted HTTPS over the Unix socket | 1,000 | 0.4988 ms |
| Added p50 | | **0.3898 ms** (limit: less than 5 ms) |

Static `CGO_ENABLED=0` build passed; ELF inspection reports statically linked
and no dynamic interpreter. The new-package race suite passed. A black-box
run of the static binary verified env-file/headless startup, owner bootstrap,
vault creation/admin access, CA fetching, socket injection and header
stripping, blind forwarding, DELETE cleanup, stable-token restart, missing-file
failure and explicit offline recovery.

The uncached complete suite passed with a private `/run` and Docker-socket
fixture. The unmodified host invocation fails the pre-existing
`TestParseAndValidateMount_RejectDockerSocket`: this host's Docker socket
symlinks into a root-only Podman directory. No upstream test or shared host
permission was changed. Reproduce the passing isolated run with:

```bash

  mount --make-rprivate / &&
```

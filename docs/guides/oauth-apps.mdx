OAuth apps are generic configuration, not a provider/scope-set catalog.
Transport authenticates as `nanoclaw-host`; every operation explicitly selects
an active native managed user whose own roles/memberships are enforced.

| API | Authorization |
| --- | --- |
| `GET /v1/managed-users/{user}/oauth-apps` | Effective user; returns `{items:AppInfo[]}` |
| `PUT /v1/managed-users/{user}/oauth-apps/{app}?scope=user` | Effective user's private library |
| `DELETE` on the same URL | Effective user's private library |
| `PUT` / `DELETE` with `scope=install` | Effective native instance **owner**, not transport owner |

Omitted scope means `user`. App IDs are canonical slugs. PUT accepts native raw
`AppInput`: `issuer`, `client_id`, write-only `client_secret`, `label`,
`authorization_endpoint`, `token_endpoint`, `token_endpoint_auth_method`,
`api_hosts`, `default_scopes`, `authorization_params`, `token_headers`, `revocation_endpoint`,
`identity`, `jwks_uri`, and `token_scope_separator`. Auth method `none` is
public-client mode; confidential identity changes require a supplied secret.

`AppInfo` retains flattened public app configuration plus `id`, `source`
(`user` or `install`), `client_secret_set`, `overrides_install`, `updated_at` and
safe usage counts. Secret values are never returned. A same-ID user config can
override an install config, but a connection pins its actual issuing source and
client. Secret-only rotation updates that central pinned client; identity
changes or app deletion mark affected connections `needs_reconnect`. Agent access
settings remain intact, but use is blocked until the owner signs in again.

## Additional token request headers

Some providers require public application metadata in HTTP headers as well as
the standard OAuth client credentials. Configure `token_headers` as a map of
header names to non-secret string values. These settings are visible in
`AppInfo`: never put client secrets, private API keys, access tokens or refresh
tokens here. Keep the client secret in its separate write-only field.

Headers are sent only to the token endpoint during code exchange and refresh,
and to the configured RFC 7009 revocation endpoint during disconnect. They are
not sent to discovery, the authorization URL, identity lookup or ordinary API
requests. GitHub's dedicated API-based revocation keeps its required HTTP Basic
authentication rather than using these headers.

For example, Stripe Link requires a publishable key in the authorization URL
and in the token/revocation `Authorization` header, in addition to the registered
OAuth client's ID and body secret:

```json
{
  "issuer": "https://login.link.com",
  "client_id": "YOUR_REGISTERED_CLIENT_ID",
  "token_endpoint_auth_method": "client_secret_post",
  "authorization_params": { "key": "pk_live_YOUR_PUBLISHABLE_KEY" },
  "token_headers": { "Authorization": "Bearer pk_live_YOUR_PUBLISHABLE_KEY" }
}
```

Apply through [Link's hosted OAuth registration](https://docs.stripe.com/agentic-commerce/agents/link-agent-wallet/oauth),
register the exact configured gateway redirect URI and supply `client_secret`
separately. For direct API connections also configure the OAuth endpoints,
`api_hosts` and scopes; MCP connections can discover endpoints from their resource.
This is not Stripe Connect or Stripe's merchant MCP.

Header names are case-insensitive, normalized on save, and must be unique.
Values must be printable ASCII. Transport/framing and cookie headers are
rejected. An `Authorization` header cannot be combined with
`client_secret_basic`, which already owns that header.

Omitting `token_headers` on update preserves them; `{}` clears them. Header-only
rotation updates existing accounts and pending exchanges without changing
client IDs, tokens, scopes or grants, just like client-secret rotation.

## Connect an API account

```http
POST /v1/managed-users/{user}/connections
Content-Type: application/json

{"label":"My API account","kind":"oauth_app","app_id":"my-app","scopes":["read"]}
```

Start consent using `POST /.../connections/{connection}/oauth/start` with
`{scopes?}`. Omitted scopes use defaults; `[]` requests no scopes. Complete
through the authenticated relay with `user_id,state,code,iss?`; the response
names `connection_id`, not an account key. See [MCP OAuth](/guides/mcp-oauth)
for callback binding, PKCE, synthetic SDK handles and central refresh behavior.

Resulting API services cover every HTTPS path at the exact configured API hosts.
Provider tokens enforce permissions; the gateway does not infer a provider
permission catalog or merge authorizations based on email/subject. Metadata
reports requested/granted scopes, provenance and verified account labels when
available. Identity lookup failure leaves account metadata null.

Explicit whole-credential grants attach references to group vaults. Owners
must also be native destination admins; recipients cannot retarget or reshare.
All current and future URL rules and owner-approved permissions apply to granted
agents automatically; the provider's actual token scopes still limit use. A group
detachment/deletion never revokes provider tokens. Global owner connection
deletion disables recipients first and reports configured upstream cleanup
failures explicitly.

Earlier `/v1/oauth-apps`, group `/oauth-apps`, `/oauth-accounts` and key-based
headless account APIs are removed, not negotiated aliases. Upstream native
non-headless local-user credential OAuth remains independent and supported.
